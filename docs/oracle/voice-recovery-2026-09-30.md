# 长时间运行后拖动语音失效（2026-09-30）

状态：已加入异常恢复与事件日志，尚未确认用户设备上的根因。

## 反馈与已知范围

用户反馈启动初期拖动能够播放语音，运行一段时间后持续无声；失效时人偶仍能正常跟随鼠标。是否发生过睡眠、音频设备切换，以及语音开关或重启能否恢复，暂时未知。

原代码在失败或超时后会清除播放状态，但仍复用同一个 QSoundEffect。人工注入持续异常时，后续请求持续失败，关闭再开启语音也不重建播放器。此前对拖动／语音逻辑加速模拟 6 小时未发现永久冷却或次数耗尽；这不是在真实音频设备上连续播放 6 小时，也不能证明用户遇到的是相同故障。

## 本次小范围加固

- 加载／播放报错、加载超过 5 秒、开始播放后超过片段时长加 3 秒时，撤销异步播放、断开旧实例的就绪回调，并通过 `deleteLater()` 释放 Qt 音频对象。
- 读取状态、设置音量、停止和播放时出现的音频异常也走相同恢复路径。清理旧对象自身失败时，仍清除其引用和播放占用。
- 只在下一次新的语音请求到来时重新创建播放器，不循环重试、不补播失败片段或积压请求。正常播放继续复用已有实例，正常松手仍允许已开始的片段播完。
- 记录事件日志：播放器创建、收到／丢弃请求、加载、开始／结束／停止、错误原因、超时阶段和异常实例释放。创建与报错时还记录 Qt 音频状态及当前／默认输出设备描述（能读取时）。

语音概率、随机等待、音量和已确认的音频切点保持原有配置。未加入后台设备轮询，也不尝试调整 Windows 应用音量或系统输出设备。

## 日志与后续排查

Windows 日志路径：`%LOCALAPPDATA%\rw_creature_pet\logs\voice.log`。

每份日志约 512 KiB，保留 `voice.log.1`、`voice.log.2` 两份滚动备份；UTF-8 编码，包含时间和进程 ID。只在事件发生时写入，不逐帧记录。目录不可写、磁盘已满等日志错误不影响桌宠；文件仅保存在本地，不自动上传。记录的文件路径和设备名可能包含个人命名，分享前可自行检查。

再次出现时，优先保留发生前后的日志及两份备份，记录大致时间，以及是否经历睡眠、耳机连接或设备切换：

- 有 `request_received` 而没有 `playback_started`：检查随后是否出现 `request_dropped`、`asset_missing` 或 `playback_error`。
- `playback_error` 后应有 `backend_discarded`；下一次新请求应有 `backend_created`。没有新请求时不创建播放器、不补播。
- 已有 `playback_started` 但仍听不到声音：该状态仅说明 Qt 报告正在播放，需要继续检查 Windows 音量混合器、设备路由和驱动，不能据此证明实际扬声器有声音。
- 长时间完全没有 `request_received`：再检查拖动反应是否产生语音请求、声音设置和运行状态，而不是直接认定音频设备故障。
